# Advanced Camera Card PR #2447 — detailed changes

## 1. Promote Call from optional per-camera mode to the single 2-way-audio entry flow

Change the product model from “some cameras have call mode” to “2-way audio starts by entering a call flow.” Dermot’s feedback consistently pushes toward making Call the canonical 2-way-audio flow instead of a parallel UX path.

### Requested implementation

* Stop treating `call_mode.enabled` as a per-camera opt-in UX mode.
* The UI path to use the microphone should always start a call session first.
* The old “direct mic on live stream” path should no longer be the normal way users talk.
* Any code branches that currently say “if call mode then X, else legacy microphone behavior” should be flattened so Call is the default/canonical path.

### Caveat to resolve

* `microphone.always_connected` was called out as the one setting that may not map neatly anymore, because it behaves like “start a call immediately on load.” That setting likely needs removal, redefinition, or constrained compatibility behavior.

---

## 2. Keep only per-camera stream selection; move the rest of call behavior to global/shared config

This is the main schema refactor. Most of the new fields were reviewed as not actually camera-specific.

### Target model

* Per-camera:

  * only the stream/intercom stream used during a call
* Global/shared:

  * mic auto mute/unmute on call start/end
  * mic navigation locking while mic is active
  * menu hiding during calls
  * button visibility through normal menu config

### Requested implementation

* Remove non-stream call behavior from the per-camera schema.
* Rehome call behavior onto existing global subsystems (`live.microphone.*`, `menu.*`, etc.).
* Update docs, editor schema, defaults, and tests to match.

---

## 3. Rename the internal concept/object from `call_mode` to `call`

The naming feedback was explicit: prefer `call` over `call_mode` for simplicity, especially for configuration objects and runtime concepts.

### Requested implementation

* Rename config object types/interfaces/classes/docs from `call_mode` to `call` where feasible.
* Rename docs file/section names so they reflect a first-class call feature rather than an optional “mode.”
* Audit localization keys and UI labels so they stop implying this is an alternate mode.

---

## 4. Delete the old menu mic button as a top-level live-view control; keep microphone control only inside the Call UI

This matches the current product decision and also resolves the review discomfort around having both a `microphone` button and a `call` button with overlapping semantics.

### Requested implementation

* Remove or suppress the old top-level menu `microphone` button for normal live view.
* Keep a mic mute/unmute control inside the dedicated call controls overlay.
* Make the top-level entry button the Call button only.

### Expected UX result

* Start talking by starting a call.
* Once inside the call UI, use the mic button there to mute/unmute.

---

## 5. Move automatic microphone behavior into `live.microphone.auto_mute` / `auto_unmute` using a `call` condition

Dermot proposed replacing bespoke per-camera call toggles with the existing declarative audio behavior system.

### Requested implementation

* Add `live.microphone.auto_mute`.
* Add `live.microphone.auto_unmute`.
* Add a `call` condition for microphone auto behavior.
* Default both to `['call']`.
* Keep `CallManager` invoking mic mute/unmute on start/end so the normal state system propagates.

### Expected result

* Starting a call automatically unmutes the mic through the shared mic behavior system.
* Ending a call automatically mutes the mic through the same shared system.

---

## 6. Drop `call_mode.auto_enable_microphone` and `call_mode.auto_enable_speaker`

These were explicitly reviewed as duplicated config once the global microphone automation behavior exists.

### Requested implementation

* Remove schema entries.
* Remove docs and editor form support.
* Remove runtime branches in `CallManager`.
* Update tests that assert these flags.

---

## 7. Move call-related navigation locking to `live.microphone.lock_navigation`

The review position was that “don’t accidentally navigate away while speaking” is a microphone-active behavior, not a call-specific one.

### Requested implementation

* Introduce or complete global `live.microphone.lock_navigation` support.
* Delete per-camera `lock_navigation`.
* Gate navigation blocking off mic-active state.
* Let calls inherit that behavior automatically because calls unmute the mic.

---

## 8. Hardcode “end call on view change” behavior and remove `end_call_on_view_change`

The feedback was to make this always true and not configurable.

### Requested implementation

* Remove schema/docs/editor/runtime support for `end_call_on_view_change`.
* Simplify view/navigation logic accordingly.
* On allowed view change, implicitly end the call first, then navigate.

### Rationale

* Keeping a hot-mic call alive after navigating away to another view was considered undesirable.

---

## 9. Hardcode “resume normal stream on end” and remove `resume_normal_stream_on_end`

The review explicitly argued this should always be true, since keeping the backchannel-enabled call stream alive after hangup risks reintroducing the bug this PR is trying to solve.

### Requested implementation

* Remove `resume_normal_stream_on_end` from schema/docs/editor/runtime/tests.
* Make hangup always restore the normal live stream.
* Delete alternate “stay on call stream after end” state transitions.

---

## 10. Remove `show_in_menu`; let normal button config control Call visibility

This was reviewed as redundant with normal menu-button enablement plus call eligibility.

### Requested implementation

* Delete `show_in_menu`.
* Use existing menu button configuration to control whether the Call button is shown.
* Determine runtime eligibility from camera capability/stream availability, not a second per-camera visibility toggle.

---

## 11. Replace `hide_menu_during_call` with global `menu.auto_hide: ['call', 'casting']`

The requested design is to express this through a condition array on the menu subsystem rather than a call-specific boolean.

### Requested implementation

* Add or complete `menu.auto_hide` condition-array support.
* Implement `call` as a menu auto-hide condition.
* Migrate casting behavior to the same system if appropriate.
* Remove `hide_menu_during_call` everywhere.

### Expected result

* Menu hiding becomes part of the shared menu condition system.

---

## 12. Collapse new call-specific actions into existing microphone actions where possible, while keeping call lifecycle separate

There are two distinct concepts that need to remain clear:

* starting/ending a call
* muting/unmuting the mic inside a call

### Requested implementation

* Keep call lifecycle actions conceptually separate: “start call”, “end call”.
* Reuse existing `microphone_mute` / `microphone_unmute` for the in-call mic control.
* Audit `call-start.ts`, `call-end.ts`, and the action factory so mute/unmute behavior is not duplicated there unnecessarily.

### Goal

* Avoid inventing parallel mic semantics while still preserving a distinct call lifecycle.

---

## 13. Revisit call automations/conditions: either drop them or replace `call_started` / `call_ended` with a single `call` condition with `state`

The review questioned whether separate `call_started` and `call_ended` conditions are needed at all and proposed a single `call` condition with a `state` parameter.

### Suggested target shape

```ts
export const callConditionSchema = z.object({
  condition: z.literal('call'),
  state: z.enum(['idle', 'connecting_call', 'in_call', 'ending_call']).optional(),
});
```

### Requested implementation

* Prefer a single `call` condition with `state` over separate `call_started` / `call_ended` conditions.
* Deprecate or remove the split condition names.
* Update docs, schema, and automation examples accordingly.

---

## 14. Simplify `CallManager` aggressively once the per-camera flags are removed

A lot of `CallManager` complexity was reviewed as a side effect of carrying per-camera options that should go away.

### Requested implementation

* Remove branches for:

  * `auto_enable_microphone`
  * `auto_enable_speaker`
  * `lock_navigation`
  * `end_call_on_view_change`
  * `resume_normal_stream_on_end`
* Fix TypeScript nullability issues, especially around `view.camera`.
* Remove the likely dead `error` state path if it is immediately overwritten by `idle`.
* Re-check the state transition model after simplification.

---

## 15. Do the media-loaded-info refactor properly, not half-way

This was one of the most substantial technical requests. The feedback was that the PR starts to make `MediaLoadedInfoManager` per-camera, but other parts of the codebase solve the same problem separately.

### Requested implementation direction

* Add `cameraID` to `media:loaded` event detail at the provider-wrapper layer.
* Store media info per camera in `MediaLoadedInfoManager`.
* Track an explicit selected camera/media slot.
* Remove call-specific `selectCurrent` behavior.
* Let consumers ask explicitly for either selected media info or media info for a specific camera.
* Remove composedPath scanning and similar hacks.
* Simplify `LiveController`, `MediaGridController`, `card.ts`, and `CallManager` around the unified model.

### High-level target API

```ts
class MediaLoadedInfoManager {
  private _byCamera: Map<string, MediaLoadedInfo>;
  private _lastKnownByCamera: Map<string, MediaLoadedInfo>;
  private _selected: string | null;

  set(info: MediaLoadedInfo, cameraID: string): void;
  setSelected(cameraID: string | null): void;
  get(cameraID?: string): MediaLoadedInfo | null;
  getLastKnown(cameraID?: string): MediaLoadedInfo | null;
  clear(options?: { cameraID?: string; all?: boolean }): void;
}
```

## 16. Make `card.ts` largely unaware of call-specific media plumbing

The top-level additions in `card.ts` were strongly disliked in review and considered a symptom of missing lower-level abstractions.

### Requested implementation

* Remove `_getMediaEventCameraID`-style top-level event path logic if the media-info refactor lands.
* Push call/media bookkeeping down into provider/media-info abstractions.
* Keep `card.ts` reacting to higher-level state rather than manually managing call-specific media routing.

---

## 17. Simplify `ViewManager` so it ideally does not know about `CallManager`

The ideal architecture described in review is one where `ViewManager` does not need explicit knowledge of `CallManager`.

### Requested implementation

* Remove bespoke call-aware navigation logic if shared mic/call state can drive it.
* If a helper remains, rename any method whose name implies it only returns a boolean if it actually performs broader side effects.
* Prefer a generic navigation policy derived from shared state.

---

## 18. Delete the custom view modifiers that only exist to support the removed alternate end-state

Several new view modifiers were reviewed as unnecessary because generic context modifiers already exist.

### Requested implementation

* Delete `call-set.ts`; replace `new CallSetViewModifier(ctx)` with `new MergeContextViewModifier({ call: ctx })`.
* Delete `call-clear.ts`; replace `new CallClearViewModifier()` with `new RemoveContextViewModifier('call')`.
* Delete `call-clear-state.ts` if `resume_normal_stream_on_end: false` support is removed.

---

## 19. Remove `removeCallState` and any logic that only supports “stay on call stream after hangup”

This was explicitly called out as dead weight if ending a call always resumes the normal stream.

### Requested implementation

* Delete `removeCallState` in `src/utils/call.ts`.
* Delete any helper logic or state-clearing code that exists only to support the removed “stay on call stream” branch.
* Remove tests that cover the obsolete behavior.

---

## 20. Keep call controls UI, but normalize its action wiring and rendering

The call controls component stays important in the new design, because it becomes the only place where the mic control lives.

### Requested implementation

* Use action dispatch consistently for both mic and speaker toggles.
* Stop handling speaker directly through controller calls if equivalent general actions already exist.
* Fix the rendering bug where external mute changes may not trigger the component to refresh.
* Pass derived primitive props from the parent, such as:

  * `speakerMuted: boolean`
  * `hasSpeaker: boolean`
* Keep component rendering tied to parent re-renders driven by the media volume-change event.

---

## 21. Move call-controls styles into SCSS and add theme variables

The styling feedback was specific: the component’s styles are non-trivial and should be treated like other components.

### Requested implementation

* Move call control styles into a dedicated SCSS file under `src/scss`.
* Add theme variables in `scss/themes/base.scss`, such as:

  * `--advanced-camera-card-call-controls-color`
  * and any related background/border/accent variables needed for customization
* Replace hard-coded styling values in the component with themed variables.

## 24. Trim documentation and examples to match the new model

The docs in the PR still describe an older per-camera “call mode” mental model and include an inline example that the review asked to relocate.

### Requested implementation

* Rewrite docs to describe Call as the canonical 2-way-audio workflow.
* Document only the remaining per-camera call setting: stream selection.
* Document global mic/menu behavior where that functionality has moved.
* Move embedded examples into `examples.md` and link to them from the main docs page.
* Remove mention of the old top-level mic-button workflow.
